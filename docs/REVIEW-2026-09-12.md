# Code audit — 12 September 2026

Independent review of the multi-store version (`982c50b`…`a44c4d3`), performed as a separate pass with reproducible
tests. Every finding below was reproduced by a failing test first;
the fix is in branch `develop`, the tests live in `tests/`. Migration notes are at the end.

## Findings and fixes

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | high | A hung synchronisation could not be stopped: `asyncio.wait_for(asyncio.to_thread(sync))` gives up waiting but cannot kill the thread, which keeps the lock and the IMAP socket forever | `run_sync()` executes `sync()` in a child process (`sync_worker.py`); on the deadline the process is killed and reaped, the lock is released, the run is journaled as `error` |
| 2 | high | Rebuild (`reprocess`) wiped expenses before parsing; a crash or restart mid-way left a silently truncated database, "healed" only by the `_REPROCESS_PENDING` marker on later syncs | `db.rebuild_expenses()` — backup, wipe and re-insert in one transaction; any parse failure, unparsed or suspicious receipt rolls the whole rebuild back. The marker is kept only for rebuilds started by older code |
| 3 | high | Rebuild safety check compared *counts* (`< 50 %` of known mails): a mailbox that lost specific mails still passed; `force` also bypassed empty/partial fetches | `db.missing_known_emails()` lists known Message-IDs (processed and failed) absent from the fetch; `force=yes` only allows those intentional deletions. Empty fetch, skipped mails or a folder warning abort even with `force` |
| 4 | medium | Order fingerprints keyed by store *name* broke on rename (`ref:<name>:<no>` vs the renamed store) and could collide between stores | `ref:store:<store.id>:<no>`; `migrate_order_fingerprints()` rewrites existing rows on start |
| 5 | medium | "Same store, same amount within ±3 days" merged independent purchases (two identical coffees) into one | Removed; merging now relies only on Message-ID and order/invoice number |
| 6 | medium | Clearing a secret in the UI deleted it from `secrets.json`, so the value from `.env` silently came back into force | `__clear__` writes a `null` override that also suppresses the environment value; new `__reset__` removes the override and restores `.env`/default |
| 7 | medium | Interval scheduling was unreachable when `.env` contained `SYNC_DAILY_AT`: saving an empty value deleted the DB row and the env value won again | Empty `SYNC_DAILY_AT` is stored explicitly; `source()` reports it correctly |
| 8 | medium | `imaplib.IMAP4_SSL()` without an SSL context does not verify the server certificate or hostname | `ssl.create_default_context()` — system trust store, hostname check |
| 9 | medium | A PDF without extractable text (scan) or a broken PDF was ignored and the mail fell through to the body-only generic parser, producing a wrong or missing total without any trace | `attachment_error` travels with the mail and into `failed_emails`; such mails become `unparsed` with the diagnostic shown under *Problem receipts* |
| 10 | medium | Cancellation/refund subjects were checked only *after* the Maxima and Wolt parsers, so a cancelled Wolt order with a PDF receipt was booked as a purchase | The `_NOT_PURCHASE` check runs first |
| 11 | low | Rebuild window ignored `failed_emails`, so the earliest failed (still unparsed) mail could fall outside the re-fetched period | `first_known_email_date()` takes processed and failed mails into account |
| 12 | low | Settings/stores could be modified while a sync was running, splitting expenses between old and new store names | Configuration writes return HTTP 409 during a sync (`_not_while_syncing`) |

## Remaining risks

- The application assumes exactly one Uvicorn worker: the lock, the scheduler and `_state` are process-local.
- Amounts are stored as `Float`; expense→store linkage is partly by name. A refunds ledger does not exist — refunds are simply not booked.
- Free-form error texts (IMAP replies, validation) and journal entries written before the i18n change remain in Russian.
- Without an admin token the settings API is open to the LAN; `test-imap` limits hosts and rate but is not a security boundary.

## Migration notes

Before deploying: stop the app and back up `data/expenses.db` and `data/secrets.json` (the latter is a secret).
On first start the schema gains `failed_emails.attachment_error` and `sync_runs.details`, and order fingerprints are
rewritten to store ids. Historical duplicates or gaps are **not** repaired automatically — review them and run an
explicit rebuild after the backup. Older code does not understand `null` secret overrides: on rollback a cleared secret
may be reactivated from `.env`.

Tests and how to run them: [TESTING.md](TESTING.md).
